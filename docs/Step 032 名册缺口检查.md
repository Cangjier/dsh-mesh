# Step 032 名册缺口检查

`.coder/members/all.md` 是人维护的名册：一个成员一节，写清 `工作区名称` / `身份` / `工作范围`
（可选 `备注`）。以前成员上下文只讲「本对话跟踪了哪些成员会话」，名册里列了、但实际没有对话的
成员完全看不见——只要主对话忘了派活，这个缺口就一直是隐形的。现在每次成员上下文快照和派活
推送都会拿名册和任务表对一遍，把缺的成员列出来，并要求把它们建出来。

## 判定

`src/lib/member-roster.mjs` 读项目目录下的 `.coder/members/all.md`（`parseMemberRoster` /
`readMemberRoster`），每个成员按下面的顺序判定：

| 情况 | 结论 |
| --- | --- |
| 已有成员会话的 `workspace` 等于名册的 `工作区名称` | 已覆盖，不报 |
| 已有会话没有工作区名（`unknown`），但 `member-scopes.json`/任务快照里的 `身份` 等于名册身份 | 已覆盖，不报（旧记录兼容） |
| 名册 `备注` 里写了 `宿主 <地址或主机名>`，而该宿主不在组网里、离线或没有在运行 DSH | 记为「暂时建不了」，不强迫 |
| 名册没写宿主，且当前**没有任何**可用成员主机（在线且运行 DSH） | 全部记为「暂时建不了」 |
| 其余 | 记为缺口，必须建 |

宿主是否可用来自 `MeshService.members()` 的快照，只在确实存在未覆盖成员时才去读，并缓存 5 分钟，
不会因为每分钟一次的快照把成员探测打爆。

## 输出

`[成员上下文]` 快照（`agent/pre-step`，60 秒一次）和 `[成员调度]` 派活推送都会多出这一段：

```text
[成员缺口] .coder/members/all.md 记录了 14 个成员，其中 3 个还没有成员对话（每个成员都必须有一个）：
- 成员5（工作区 ai-cad-web1，身份 前端开发1）还没有成员对话：call_member { "workspace": "ai-cad-web1", "identity": "前端开发1" }，工作范围按名册里的写。
...
[成员缺口] 名册里 1 个成员暂时建不了对话：成员10（宿主 10.66.66.3 当前不可用（离线或没有在运行 DSH））。
```

- 缺口存在时，即使本对话当前**没有**任何进行中的成员会话，快照也会注入（这是它存在的意义）；
  名册里全部成员都有对话时，行为和以前完全一样（没有进行中会话就不注入）。
- 已覆盖的成员不重复列出；建好的下一次快照就消失。
- 派活推送额外写一条规则：名册里列出但还没有成员对话的成员必须建出来，除非宿主明确不可用。

## 验证

- `test/member-roster.test.mjs`：解析（主对话 / 成员节 / 无工作区的块忽略 / 备注里的宿主）、
  按工作区覆盖、按身份覆盖旧记录、缺口输出、宿主离线 / 不在组网 / 全员不可用三种豁免、
  没有名册时不报。
- `test/member-context.test.mjs`：只有名册缺口时也会注入快照；成员会话覆盖工作区后不再注入；
  派活推送带上缺口段落和「必须建出来」规则。
