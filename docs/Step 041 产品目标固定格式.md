# Step 041 产品目标固定格式

`set_product_stage` 的三个目标（产品 / 开发 / 研究）原来是自由文本，容易出现「可用的成员面板」
这种只有结论、没有现状、也无法判断是否达成的写法。现在目标文本固定为：

```text
<类别> 现状 <现在怎样>，预期 <要变成怎样>。
```

类别是目标所属的产品面，常用 `应用功能` / `应用界面` / `应用服务` / `算法` / `数据` / `性能` /
`稳定性` / `安全` / `兼容性` / `工程质量` / `体验` / `交付` / `文档`；也接受其他短类别词
（例如 `内核`、`成本`）。类别不是白名单，这组只是提示。

## 行为

- 写入 `text` 时校验格式；不符合就抛错，`set_product_stage` 返回 `ok:false`、阶段状态不变。
  错误里给出固定格式、常用类别和一条完整例子，并带上被拒绝的原文（最多 80 字符）。
- 符合格式的文本会**规范化**后保存：
  - 类别与「现状」「预期」之间的冒号（`：` / `:`）去掉，统一成一个空格；
  - 「现状」描述与「预期」之间的分隔符接受 `，` `,` `；` `;`，统一成 `，`；
  - 去掉「预期」末尾多余的句号/逗号/分号，统一补一个 `。`。
- 例：`应用功能：现状 只能做基础建模；预期 支持参数化特征` →
  `应用功能 现状 只能做基础建模，预期 支持参数化特征。`
- 只更新 `status`、不传 `text` 时不做格式校验，也不改动已存文本；`text: ""` 仍然表示清除该目标。
- **已存在的自由文本不会被改写**：读取和展示沿用原样，只有下一次显式写 `text` 时才要求新格式。
- 文本长度上限仍是 300 字符，先按原文判断，再按规范化后的文本判断一次。
- 成员上下文的产品阶段块在目标行后增加一行提示：
  `- 目标文本格式：<类别> 现状 <现在怎样>，预期 <要变成怎样>。（类别如 应用功能 / 应用界面 / 应用服务 / 算法 / 数据 / 性能 / …）`
  工具描述和 `goals.*.text` 的 schema 描述也带同样的格式与例子。

## 校验规则

正则（`u` 模式）：

```text
^(.{1,20}?)[\s：:]*现状[\s：:]*(.+?)[，,；;]\s*预期[\s：:]*(.+?)[。.]?$
```

- 类别不能为空，不能含 `，` `,` `。` `；` `;` 或换行，最多 20 字符（不含冒号）；
- 「现状」和「预期」的描述都不能为空；
- 缺少类别、缺少「现状」、缺少「预期」、缺少中间逗号，都会被拒绝。

## 边界

- 类别不做白名单，避免把「等等」里的新类别挡在外面；格式本身足够约束「先现状、后预期」。
- 目标文本是产物描述，不是状态机字段；状态仍是未开始 / 进行中 / 已达成 / 未达成，互不影响。
- 已有 `product-stages.json` 不需要迁移；旧文本可读、可只改状态，下一次改文本时按新格式写。
